# Overview

Use the [Management API](/technical/platform-integrations/rest-apis/index) to create an integration campaign and its component hierarchy directly in Extole. Take this path when you are building an integration for one client account rather than shipping it as a packaged bundle in Extole's integration library.

An API-created integration is still a component-based integration, so it follows the same rules as a packaged one:

- **Reusable component types**, rather than one-off controllers written for a single partner.
- **Typed sockets** — the named attachment points on a component that accept only components of a declared type, such as a `views` socket that holds view components. [Create the Integration Campaign and Component Model](/technical/building-custom-integrations/integration-lifecycle/integration-component-model) describes each socket this build uses.
- **Business-event templates** — maintained components that produce a canonical Extole event such as `converted` or `shipped`, duplicated into your campaign instead of rebuilt. [Integration Categories](/technical/building-custom-integrations/integration-types/integration-categories) explains how a partner's own event names map onto them.
- **v10 component types**, the current generation of the integration component model. Type names carry the generation as a suffix, as in `integration-v10.1` and `config-view-v10.0`.
- The same **naming conventions and validation rules** a packaged integration passes before it is published.

Examples in this guide use a generic partner named `example`. Substitute the real partner name, event names, and field names from that partner's own documentation.

When this documentation set has a page for your partner, read it first. The partner page carries the wire contract for that platform — event names, payload fields, and status mapping — while this guide carries the build sequence that applies to every platform. Partner pages use the partner's name as the page slug, so you can open one directly instead of searching for it.

## Decide Whether You Are Installing or Building

Creating an integration-shaped campaign and installing a registered integration are distinct outcomes. The
distinction matters as soon as you expect the result to appear on the My Extole
[Integrations page](https://my.extole.com/integrations).

| Outcome you want | What to do | What makes it appear |
| :--------------- | :--------- | :------------------- |
| A registered integration every client can find and install | Publish the partner's integration component to the Extole-owned library. | An Extole-owned component tagged `internal:type:integration` and `internal:self-managed`. |
| An installed instance for this client | Duplicate the library source, or build the campaign and component tree yourself. | A non-root component owned by this client, tagged `internal:type:integration` and `internal:self-managed`. |
| A development-account build to inspect, configure, or test through the campaign and component APIs | Create the campaign and component tree directly. | The same client-owned component; it is visible to this client only. |

The Integrations page selects built components by the tag `internal:type:integration`. Among those, it
treats a component as this client's installed integration when the component's source client is this
client, and as an available type to install when the source client is Extole. Two further conditions
decide whether a client-owned component shows up at all:

- **Root components are excluded.** The integration component must be a child of the campaign root,
  never the root component itself.
- **Without `internal:self-managed` the entry renders as unavailable** rather than installed.

The tags that decide visibility therefore sit on the non-root integration component. A build that
follows the component model in these guides is visible; one that puts the integration tags only on the
campaign, or only on the root component, is not.

`internal:integration-component-name:<component-name>` is a separate, older convention. Library bundles
carry it on the integration campaign so an installed copy can be traced back to the component it came
from, and this guide keeps it for parity with those bundles. The Integrations page does not read it, so
setting it does not make a build appear and omitting it does not hide one. It is not the fix for a build
that is missing from the page — check the component's tags, its owner, and whether it is the root.

Building the tree in one account does not register a new partner for anyone else. When you need a new
installable partner that every client can see, build and validate the shape in a development account
first, then publish the reusable component to the Extole-owned library. Until that publish happens, the
account-local build is not an installable integration.

## Choose the Integration Category First

Place the platform in a category before creating anything. [Integration Categories](/technical/building-custom-integrations/integration-types/integration-categories) describes what each category contains and how to recognize it; this guide carries the API sequence that builds it. Pick the path from discovery, not from habit.

| Category | When it applies | Build path |
| :------- | :-------------- | :--------- |
| Outbound library install | The duplicatable listing already has an integration component whose name matches the partner. | Duplicate that library component with no target campaign, reshape it to the finished shape on the partner page, then attach webhooks and credentials. See [Build an Outbound Library Integration](/technical/building-custom-integrations/integration-types/integration-build-outbound). |
| Reward fulfillment | The partner supplies gift cards, prepaid cards, points, or payouts that Extole orders when a reward is earned. | Install the maintained source when one exists; otherwise build the supplier type, the support campaign of supplier templates, and the integration with its `REWARD` webhooks. See [Build a Reward Fulfillment Integration](/technical/building-custom-integrations/integration-types/integration-build-reward-fulfillment). |
| Inbound custom build | No maintained source exists for the partner, or the platform maps wire events onto canonical business events. | Create an `INTEGRATION` campaign from the custom integration template, then add business events, trigger rules, data capture, and views. This is a client-local build unless a registered integration component is published separately. |

Before creating anything, query the duplicatable listing for integration components and look for one whose name matches the partner. Match on the component name, not on a fixed type version: the integration type is revised over time, so a source may be typed `integration-v10.0`, `integration-v10.1`, or a later revision, and a query pinned to one revision reports a maintained partner as missing. Prefer that name match over building from `custom_integration`. Rebuilding a maintained partner from the custom template produces a campaign that looks related and does none of the partner's webhook or credential work.

A request that adds inbound scope to a maintained outbound partner uses both paths: install the library source first, then add business events to the installed campaign using the inbound sequence.

## Rules Every Build Follows

These hold on every path, whether you make the calls by hand, from a script, or from a tool acting on your behalf.

### Settle the Scope Before the First Write

Know the client and environment you are building in, the partner platform and its version, whether the integration is inbound, outbound, or both, which events it carries, and who owns the partner credential. Each of these decides part of the component model, so discovering one late means rebuilding rather than extending.

Read the partner's current documentation and confirm the event hooks for the version you are integrating. Hook names and payload shapes change between versions of the same platform, and they do not carry across platforms.

Inspect the target client before creating resources. An active integration whose campaign and component identity already match what you need is the one to extend. Archived campaigns are not candidates for reuse: they receive no events, and an archived campaign holds no program label against a new campaign, so its label is free for the campaign you are about to build.

### Start From a Maintained Source When One Exists

A library install is the beginning of the reshape, not the end. The source ships the union of what every account might want, so finishing it means creating the partner's component type, deleting the library children this account does not use, publishing, and creating the webhooks. A campaign left at the raw install carries more children and fewer webhooks than the partner page describes.

Resolve library components by name at build time rather than storing their identifiers as fixed values in scripts or notes. The library revises those components, and a hardcoded identifier goes stale without failing loudly.

### Mutate Through Campaign Versions

Every campaign mutation creates a new version, and a version-scoped endpoint rejects a stale one. Refresh the version before each mutation, as [Use Roll-Forward Campaign Versions](#use-roll-forward-campaign-versions) describes.

### Build From Components, Not Controllers

Use the reusable business-event, rule, and data components. A custom controller written where a template already implements the behavior is code that Extole cannot upgrade or validate on your behalf.

Every integration carries a `views` socket and the same three baseline views: a configuration view exposing the settings that complete partner setup, a report-runner view charting what the integration processes, and an event-stream view carrying its live feed. What the partner does decides what the report counts and what the feed filters to, never whether the tabs exist. A category can add to that baseline — a reward fulfillment partner carries a fourth view, a second configuration view named `reward-suppliers` that exposes the supplier socket — but never subtracts from it.

Create reward suppliers, client keys, and webhooks only for an outbound flow the integration actually has. An inbound integration needs none of them, and creating them for completeness leaves credentials and unused resources for someone to reconcile later. A reward fulfillment partner is the opposite case: its suppliers, `REWARD` webhooks, and credential setting are the integration rather than extras on top of it.

### Keep the Two Event Vocabularies Apart

Partner input event names and canonical Extole business event names are separate namespaces. The trigger rule carries the name that arrives on the wire; the business event carries the Extole name the rest of the platform understands, such as `converted` or `shipped`. Renaming a business event to match a partner's wire name breaks every program and report that reads the canonical name.

Decide who shapes the inbound payload before you write the partner-side setup instructions. An extension or service written for this integration can send Extole-shaped events. A partner's own webhook sends whatever the partner defined, and reconciling that shape happens inside Extole with a prehandler — see [Normalize Inbound Events with a Prehandler](/technical/building-custom-integrations/integration-types/integration-prehandlers). Asking the client to build a translation service in front of Extole is a deliberate design decision, not the default.

### Map Every Field You Persist

Map fields explicitly, in the same pass that creates the business events. A business event with an empty `data` socket produces an event with no transaction identifier, no person key, and no value, so nothing downstream can deduplicate, attribute, reward, or report on it.

Assign key types from what a field means, not from how it is spelled. A partner field named `customer_id` can hold the partner's own account identifier rather than a value that should resolve an Extole person.

### Test Before You Publish

Build and inspect the complete campaign, then test every inbound event and every configured outbound path. Keep the identifiers as you go — campaign, components, external resources, and test events — so you can verify the build and clean up its test data afterwards.

Keep secrets out of the campaign itself. Access tokens, partner secrets, and private client values do not belong in component descriptions, logs, or example payloads; a webhook client key or a protected setting is where they go.

## Gather What the Build Needs

Most of what a build needs is readable before you start, and the partner's name is what unlocks it: the name selects the partner page, and the partner page gives you the category, the wire contract, and the finished shape.

| Value | Where it comes from |
| :---- | :------------------ |
| Partner platform and version | The partner page for this partner, then the partner's own developer documentation for hooks and version differences. |
| Integration category | [Integration Categories](/technical/building-custom-integrations/integration-types/integration-categories), which fixes the shape the rest of the build takes. |
| Access Token | A server-side access token, created in the [Security Center](https://my.extole.com/security-center), authorized to manage campaigns and components and to read people during verification. |
| Extole API host | The production host for campaign, component, and event calls, held in `EXTOLE_API_HOST`. |
| Target client | The account your access token authenticates to. Confirm it before the first write — a token pointed at the wrong account builds a live integration there. |
| Integration name and component name | Derived from the partner name — a human-readable campaign name and a stable lowercase component name. |
| Program label | Derived from the integration name, unique and stable, used to target events to the integration. |
| Inbound event contract | The partner page, then the partner's developer documentation: event names, identity fields, unique identifiers, and values. |
| Canonical business events | Extole names such as `converted`, `shipped`, or `canceled`, chosen to match the outcome each partner event describes. |
| Field mapping | The documented partner contract, mapped source-to-destination for every captured field. |
| Partner configuration | The partner page names which settings the integration exposes, such as store URL, account identifier, endpoint, or status mapping. Their values are configured afterward and do not block the build. |
| Outbound requirements | The partner page, when the category calls for outbound behavior: destination, trigger, authentication, retry contract, and owning program. |
| Publication approval | Your own release process. Where approval is outstanding, build the campaign to a draft and finish it when approval arrives. |

Three values have no source you can read: a partner-side secret, an account identifier the partner issues, and the logo artwork. Build everything that does not depend on them and track those three as outstanding, rather than waiting on the whole table before you start.

## One Host, Two Access Tokens

Management calls and event submission share one host. Every example in this guide reads it from this variable:

```bash
EXTOLE_API_HOST=https://api.extole.io
```

Campaigns, components, webhooks, and reward suppliers are Management API calls; event submission is a Server to Extole call. Both go to `api.extole.io`, as described in [REST APIs](/technical/platform-integrations/rest-apis/index). [Send Platform Events to Extole](/technical/building-custom-integrations/integration-types/sending-platform-events) covers the sending side in full.

One host does not mean one credential. Use separate access tokens for integration management and event submission: the partner application receives only the token that can submit events, never the one that can manage campaigns and components.

## Use Roll-Forward Campaign Versions

Campaign mutations create a new version. A version used by one successful request is stale for the next request.

Refresh the version before every version-scoped mutation:

```bash
CAMPAIGN_VERSION=$(
  curl --silent --show-error --fail-with-body \
    "$EXTOLE_API_HOST/v2/campaigns/$CAMPAIGN_ID" \
    --header "Authorization: Bearer $MANAGEMENT_API_ACCESS_TOKEN" |
  jq --raw-output '.version'
)
```

Use the singular path segment `/version/{version}`:

```text
/v2/campaigns/{campaign_id}/version/{version}/components
```

Do not use `/versions/`. If the API returns `stale_version` or `concurrent_update`, retrieve the campaign again, reconcile the latest state, and retry only the intended mutation.

## Discover Reusable Components

Find templates at execution time through the duplicatable-components endpoint. This endpoint returns components that the current client can duplicate, including components made available through subscriptions and grants.

```bash
curl --get "$EXTOLE_API_HOST/v1/components/duplicatable" \
  --header "Authorization: Bearer $MANAGEMENT_API_ACCESS_TOKEN" \
  --data-urlencode "name=template_transacted_business_event" \
  --data-urlencode "version_state=PUBLISHED" \
  --data-urlencode "having_any_types=business-event-v10.0" \
  --data-urlencode "show_all=true"
```

After the target component and socket exist, add `target_component_id` and `target_setting_name` to return only components compatible with that socket. Do not use the deprecated `target_socket_name` parameter. Narrowing this way is the reliable form of the query, because a widely used source such as `input_event` also appears once for every campaign that already installed a copy of it.

Use these reusable sources:

| Component | Program label | Purpose |
| :-------- | :------------ | :------ |
| `template_transacted_business_event` | `business-events` | Revenue or transaction outcome. |
| `template_tracked_business_event` | `business-events` | Non-revenue lifecycle milestone. |
| `input_event` | `rules` | Matches one or more partner input event names. |
| `business_event_data` | `business-events` | Captures one mapped field. |
| `event_id` | `business-events` | Captures the Extole event identifier when required. |

Validate each candidate's type before duplicating it, and prefer the v10 type when a legacy version of the same name is also returned.

Several results carrying the same name and the same v10 type are copies of one maintained source — one per campaign that already installed it — rather than a choice between behaviors. Narrow by the target socket and duplicate the maintained source. Two cases are worth stopping on: discovery returns no published match of the required type, or two genuinely distinct components could satisfy the request and the choice would change behavior.

## Confirm the Build Is Finished

By the end of a build you can name each of these, and a gap in the list is an unfinished integration:

- The environment and client you built in.
- The campaign identifier, current version, state, and program label.
- The root and integration component identifiers.
- The canonical business events and the partner trigger names that reach them.
- The field mappings and key types.
- The view components and the settings they display, including the report runner behind the activity view and the event stream behind the event view, each with the identifier its view resolves to.
- The external resources created, or confirmation that the category needed none.
- The programs whose business events the integration replaced or added to, or confirmation that it is not yet connected to a program.
- The test event identifiers and what verification showed.
- The partner page this build implements.
- The partner-side steps that remain.

A campaign still in draft, a disabled webhook, a placeholder URL, or an event that has not been tested end to end each mean the integration is not yet live. [Validate and Publish an Integration](/technical/building-custom-integrations/integration-lifecycle/integration-validation) covers that gate.

---
title: "Event Dated Before the Referral Is Unattributed"
description: "Why an uploaded event can reach a referred friend and still be recorded unattributed when the time it carries is earlier than the friend's referral."
---

# Overview

An event reaches the right person and is saved, but it is recorded unattributed, and no reward follows. The person was referred, and the referral is valid. Other events for the same person, sent in the same file, may even have been attributed. This page covers one cause: the event carries a time from before the person's referral existed.

## Why the Event Time Matters

When an event sent into Extole carries a time other than the time it arrived, Extole attributes it using the time it carries. In a direct file upload, that time comes from the `event_time` column, and a row with no `event_time` takes the time the file is processed. See [File-Based Events](/technical/platform-integrations/files/file-based-events).

So an event can arrive weeks after the date it carries. A file that sends a qualification on the day it is earned, but dates it to the day the account opened, does this on every row.

When a row from a direct file upload carries a time other than the time it arrived, Extole leaves out the friend's referrals created at or after that time, and the friend's journeys created at or after it, other than a journey this event starts. If the friend's referral was created later than the event time, the event is treated as having happened before the friend was referred, and it is recorded unattributed.

On a direct file upload, a date with no time of day resolves to the start of that day in your account's time zone. That makes this cause likely: a row dated to the start of the day is earlier than a referral made later that same day.

A Flow Builder file integration can include a **Delayed Event**, which holds the rows for the event it is named for and sends each one when its date arrives. A row with no `event_time` waits for the **Delay** you set. A row whose date has already passed waits for the **Delay** if the date is inside the **Lookback Window**, and is not sent if it is older. With a **Delay** of zero, neither row is held. A held row is sent again as an event Extole raises itself, dated to the time it is sent, so this check does not apply to it. A row that is not held is an uploaded event like any other, and the check applies. See [Delay a File Event](/technical/platform-integrations/extensions/file-integration#delay-a-file-event).

## Why Another Event Can Still Attribute

A business event with an eligibility window holds each event for the length of the window, 24 hours unless the campaign sets another length, and then sends it again as an event Extole raises itself. The resent event keeps its original date, but this check applies only to events sent into Extole, so the friend's referral counts if it exists by the time the window ends.

A business event without an eligibility window takes the uploaded event as it arrives, so the check applies. So the same person's account opening, with the same date, can be attributed while their qualification is not. An attributed event for the same person does not rule this cause out. Check which business events in the campaign have an eligibility window.

## How to Confirm It

For each unattributed event, compare two times:

1. The event time recorded for the event.
2. The time the friend's referral was created.

If the event time is earlier in every unattributed case, and later in the attributed cases, this is the cause.

## What to Do

The file's sender can fix it: send the actual time of the event in `event_time`. If only the date is known, send the end of that day, `23:59:59`, rather than its start.

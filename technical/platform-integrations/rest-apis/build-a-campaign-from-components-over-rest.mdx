# Overview

When no template has the flow you need, start from the **Custom Campaign Template** and add
components to it with the calls on this page, in order.
[Building a Marketing Campaign](/technical/configuring-extole/building-a-marketing-campaign)
covers what to build: the roles, journeys, business events, and rewards, and the rule that
evaluates each condition.
[Configuration Concepts](/technical/configuring-extole/configuration-concepts) explains components.

## Start from the Custom Campaign Template

[List duplicatable campaigns](/api-reference/campaigns/list-duplicatable-campaigns) returns the
templates your account can copy. Select the row whose `name` is `Custom Campaign Template`. Match
on the name, because other templates can share its `program_type`, `empty-campaign`.

[Duplicate a campaign](/api-reference/campaigns/duplicate-a-campaign) creates your copy as a
draft. Send the `name` of the new campaign and the `program_label` of the program it belongs to.

| Component | Absolute name | What it is |
|---|---|---|
| Root | `/` | The campaign, of type `campaign-v10.0`, with the `roles` socket. |
| Placeholder Role | `/placeholder_role` | One role, to rename or replace. |
| Placeholder Journey | `/placeholder_role/placeholder_journey` | One journey in that role. |
| Template Business Event | `/placeholder_role/placeholder_journey/template_business_event` | One business event in that journey. |

[Create a campaign](/api-reference/campaigns/create-a-campaign) makes a root component with no
type. A Flow Builder campaign needs `campaign-v10.0` on its root, and the template supplies it.

## Add Each Component After Its Parent

| Order | Component | Parent | Socket |
|---|---|---|---|
| 1 | Role | The root, `/` | `roles` |
| 2 | Journey | A role | `journeys` |
| 3 | Business event | A journey | `businessEvents` |
| 4 | Reward | A role | `rewards` |
| 5 | Reward rule | A reward | `rewardRules` |
| 6 | Action | A business event | `actions` |

For each component:

1. Call [List duplicatable component summaries](/api-reference/components/list-duplicatable-component-summaries)
   with `target_component_id` set to the parent's id and `target_setting_name` set to the socket.
   The response lists only the sources that fit that socket.
2. Choose the source. The template sources are `template_role`, `template_journey`,
   `template_tracked_business_event`, and `reward_core`. When two rows share a name, take the row
   whose `owner` is `EXTOLE`.
3. Call [Duplicate a component](/api-reference/components/duplicate-a-component) with
   `target_campaign_id`, `target_component_absolute_name` for the parent, `target_setting_name` for
   the socket, and `component_display_name`. The copy takes its name from the display name:
   `Member Joined` becomes `member_joined`.
4. Set the copy's values with
   [Component Settings Over REST](/technical/platform-integrations/rest-apis/component-settings-over-rest).

A copy brings the children of its source. `reward_core` arrives with its reward rules, and
**Publish Event Data** arrives with a person identification.

For the promotion and the invitation, copy these sources:

| Part of the flow | Source | Parent | Socket | What arrives with it |
|---|---|---|---|---|
| The promotion is viewed and clicked | `promotion_viewed` and `promotion_clicked` | A journey of your own | `businessEvents` | The two business events |
| The invitation is shared | The `share` journey | The first person's role | `journeys` | `shared`, the share emails, the share link, and a targeting scenario |
| The invitation is clicked | The `new_customer` journey | The second person's role | `journeys` | `share_clicked` and its landing destination |

Set `sequence` on every journey, in the order of your flow across the roles, because a copy keeps
the number of its source. `sequence` on a business event orders the events of a journey, and on a
role orders the columns.

## Set the Trigger of Each Business Event

The **Triggered By** setting, `triggerEvent`, names the trigger event that starts the business
event. For an event your backend sends:

1. Find the **Event API** extension: [List campaigns](/api-reference/campaigns/list-campaigns)
   returns it as a campaign of type `EXTENSION`, and its `event_api` component has the
   `integrationEvents` socket. If the account already declares the event's name there, reuse that
   declaration and go to step 4.
2. Copy a declaration into `integrationEvents`. List the duplicatable component summaries for that
   socket: the rows of type `event-api-trigger-event-v10.0` include named events, such as
   `account_opened`, and `event_api_trigger_event` for a name of your own. Set
   `component_display_name` so that the copy's name is the exact event name your systems send:
   `Member Joined` becomes `member_joined`.
3. Publish the Event API campaign with [Publish a campaign](/api-reference/campaigns/publish-a-campaign).
   A business event selects from another campaign's published version only.
4. Call [List selectable components](/api-reference/components/list-selectable-components-for-a-component-reference-list)
   for the business event's `triggerEvent` setting, and then
   [Select components for a component reference list](/api-reference/components/select-components-for-a-component-reference-list)
   with the declaration's id in `component_ids`.

A business event with a selection starts on that trigger event alone and needs no input-event
rule. A business event that another business event or **Publish Event Data** starts selects that
business event in **Triggered By**. For a website tag, an app, or a file, declare the event on the
matching extension, as
[How to Set Up Triggered By](/guides/flow-campaigns/how-to-set-up-triggered-by) describes, and
select it the same way.

## Add the Rules

Each rule is a component that you copy into its socket:

| Rule or action | Parent | Socket |
|---|---|---|
| A trigger rule, such as **Has Taken Action** with a **Minimum Action Age** | A business event | `triggerRules` |
| A unique event key: the `event_id` data item, with the copy named after the field that holds the key, such as `membership_id` | A business event | `data` |
| A reward rule, such as **Has Taken Action** with a count or a total, or **Reward Limit** | A reward | `rewardRules` |
| **Publish Event Data** | A business event | `actions` |
| A person identification | **Publish Event Data** | `personIdentification` |

**Has Taken Action** exists as a trigger rule and as a reward rule. The summaries for the socket
you are filling list the one that fits it.

## Give Each Reward a Supplier, a Delivery, and an Email

1. Call [Create a reward supplier](/api-reference/reward-suppliers/create-a-reward-supplier). For
   a reward that your own systems deliver, such as an account credit or a free month, send
   `reward_supplier_type` `CUSTOM_REWARD`, a `type` of `ACCOUNT_CREDIT` or `LOYALTY_POINTS`, a
   `face_value_type`, and a `face_value`.
   [How to Reward with Account Credits](/guides/rewards-management/setting-up-your-rewards/how-to-reward-with-account-credits)
   describes custom rewards.
2. Set the reward's `rewardSupplierId` to the supplier's `id` with
   [Update a component setting](/api-reference/components/update-a-component-setting).
3. Select the business event that earns the reward in the reward's `triggerEvent`.
4. Copy `reward_issuer`, **Reward Emails**, into the reward's `rewardIssuer` socket, then copy
   `reward_email` into that copy's `sendActions` socket.

### Use a Placeholder Supplier Until Fulfillment Is Connected

A custom reward with `auto_fulfillment_enabled` and `reward_email_auto_send_enabled` set to `true`
is fulfilled and sent inside Extole, with no call to your systems. Create one for each reward in a
new campaign, so a test person earns the reward and receives the reward email before your
fulfillment exists. Replace it when your fulfillment is ready.

## Remove the Components You Do Not Use

[Delete a component](/api-reference/components/delete-a-component) removes a component and its
children. Deleting the root component archives the campaign.

## Read the Campaign Back and Test It

[Get a built campaign](/api-reference/campaigns/get-a-built-campaign) returns the campaign with
every setting evaluated. Read it to confirm that each business event has its trigger and each
reward its rules and supplier.

The campaign stays a draft until you publish it.
[Test a Campaign Draft Over REST](/technical/platform-integrations/rest-apis/test-a-campaign-draft-over-rest)
covers how to test it: send the events to `campaign-<campaign id>-production` to see each reward
from its own supplier, and back-date events with `event_time` to test each window from both sides.
[Campaign States Over REST](/technical/platform-integrations/rest-apis/campaign-states-over-rest)
covers how to publish and launch.

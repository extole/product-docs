# Overview

A campaign sandbox runs a campaign's latest version, including changes you have not published
yet. Live traffic keeps the published version. To test a draft before you publish it, send the
events of a test journey, such as a share, a share click, a signup, and a conversion, to a
campaign sandbox. To see what the published version does with the same events, send them to a
production sandbox.

## Choose a Sandbox

| Sandbox | Value | Campaign version | Container |
|---|---|---|---|
| Campaign preview | `campaign_preview-<campaign id>` or `campaign_preview-<campaign id>-<journey name>` | Latest, including unpublished changes | `test` |
| Campaign | `campaign-<campaign id>-<container>` or `campaign-<campaign id>-<container>-<journey name>` | Latest, including unpublished changes | The container you name, such as `test` |
| Production | `production-<container>`, such as `production-test` | Published | The container you name |

The campaign id is in the campaign's address in My Extole, after `/campaigns/`.

If a request sends no sandbox, Extole uses a production sandbox: `production-production`, or
`production-<container>` when the request names a container. Such a request runs the published
version, not your draft.

The two campaign sandboxes differ in who can enter a journey and which rules run:

- **Campaign preview**: a person can enter a journey without a referral, so you can test a friend
  journey without an advocate. A journey name in the value, such as `FRIEND`, gives that journey
  the highest priority. The campaign's quality rules do not run.
- **Campaign**: journey entry follows the campaign's own rules. A friend enters the friend journey
  only through a referral, as on your live site. The campaign's quality rules run.

Use the campaign preview sandbox to check that each part of a journey runs and renders. Use the
campaign sandbox to check who enters a journey and what the quality rules stop, and send the same
events to a production sandbox to compare the draft with the published version. To test a draft's
rewards with the suppliers they name, use the campaign sandbox with the `production` container:
`campaign-<campaign id>-production`.

## Send an Event to a Sandbox

### Consumer Events

On the consumer API, pass the sandbox in the `X-Extole-Sandbox` header. Send every request of one
test journey with the same header.

```bash
curl -X POST "https://<your program domain>/api/v6/events" \
     -H "Authorization: Bearer <access token>" \
     -H "Content-Type: application/json" \
     -H "X-Extole-Sandbox: campaign_preview-<campaign id>-FRIEND" \
     -d '{"event_name": "signed_up",
          "data": {"email": "friend@example.com", "shareable_code": "<advocate code>"}}'
```

### Server Events

For an event your server sends to `https://api.extole.io/v6/events`, put the sandbox in the
event's data as `sandbox`. The `X-Extole-Sandbox` header applies only to the consumer API. Use a
server-side access token, as in [Send Events from the Partner Platform](/technical/building-partner-integrations/integration-types/partner-events-send-from-platform).

```bash
curl -X POST "https://api.extole.io/v6/events" \
     -H "Authorization: Bearer <server access token>" \
     -H "Content-Type: application/json" \
     -d '{"event_name": "converted",
          "data": {"email": "friend@example.com",
                   "partner_conversion_id": "<order id>",
                   "sandbox": "campaign-<campaign id>-test"}}'
```

A consumer event can carry `sandbox` in its data too. Extole ignores a value that does not match a
sandbox format above and processes the event as if it named no sandbox.

### Test a Referral

To test a referral in the campaign sandbox, the second person needs the first person's real share
code. Create one with [Create a person shareable](/api-reference/persons/create-a-person-shareable)
for the first person, then send the second person's events with that code as `shareable_code`, in
the same sandbox. The share link ties the two people, as it does on your live site.

### Send an Event That Took Place Earlier

To test a time window, give a server event an `event_time` in ISO 8601. Extole records the event
at that time. The **Recent Activity Window** and **Minimum Action Age** of **Has Taken Action**
count back from the time of the event being evaluated, so a back-dated event lands inside or
outside them as it would have on that date. **Reward Limit** counts rewards by when they were
earned, which is when Extole processed the event.

A window counts back from the event and has no end, so it also counts a later-dated event that is
already on the profile. Send the events of one test person one at a time, oldest first, and read
the person's steps until the last event's business event or reward evaluation shows before you send
the next. Events sent together can be processed in any order.

To show that a 60-day window holds, test two people: one who opened an account 50 days ago and
buys today, who earns the reward, and one who opened 70 days ago and buys today, who does not:

```bash
curl -X POST "https://api.extole.io/v6/events" \
     -H "Authorization: Bearer <server access token>" \
     -H "Content-Type: application/json" \
     -d '{"event_name": "account_opened",
          "event_time": "2026-09-10T17:00:00Z",
          "data": {"email": "late-tester@example.com",
                   "sandbox": "campaign-<campaign id>-production"}}'
```

### See How Extole Processed an Event

To see each decision Extole made for a test event, such as which sandbox and campaign it used and
which rules passed, ask for the processing log:

- On the consumer API, add the `X-Extole-Debug` header or the `debug` query parameter with any
  value other than `false` or `0`. The response returns the log in `X-Extole-Log` headers. The
  value `trace` adds timing and trace detail.
- On a server call, add the `X-Extole-Debug` header with a level from `1` to `3`, as
  [Common Errors](/api-reference/getting-started/common-errors) describes.

```bash
curl -i -X POST "https://<your program domain>/api/v6/events?debug=true" \
     -H "Authorization: Bearer <access token>" \
     -H "Content-Type: application/json" \
     -H "X-Extole-Sandbox: campaign-<campaign id>-test" \
     -d '{"event_name": "share_destination", "data": {"advocate_code": "<advocate code>"}}'
```

## What a Test Event Does

A sandbox changes which campaign version handles the event and which container records it. The
event is processed in full:

- In the `test` container and in the campaign preview sandbox, a reward comes from your account's
  test reward supplier, with that supplier's value, whatever supplier the campaign's reward names.
  The test reward supplier is the reward supplier named `Default Test Reward`. If your account has
  no test reward supplier, the reward is not issued. A rule that counts a person's earlier rewards
  counts only rewards in the same container.
- In the `production` container, a reward comes from the supplier that the campaign's reward
  names, with its value. To test a draft's reward, its value, and its reward email, send the events
  to the campaign sandbox `campaign-<campaign id>-production`. The draft stays unpublished.
- When one person's event publishes an event to another person, the published event keeps the
  sandbox of the event that caused it. Extole then evaluates the second person's reward in that
  container, so send every event of one test to the same container.
- Emails and webhooks run as they do for a live event. Use test email addresses that you control.
  See [Exclude Test Data from Analytics](/technical/operational-tasks/program-testing/exclude-test-data-from-analytics)
  for how test containers are reported.
- An event can start schedules, such as a reward's pending period or a reminder email, which run
  later. After a test, cancel the schedules it started and check that each test person has no
  reward. When a **Pending Period** ends, Extole runs the reward's rules
  again if the reward's evaluation started more than 10 minutes earlier. To test a pending period
  without waiting for it, set the draft's **Pending Period** to 11 minutes, send the test events,
  including any that should stop the reward during the period, read the result after the period
  ends, and set the period back.
- Your account's prehandlers still apply, so a prehandler can record an event in another
  container than the one the sandbox names.

To check a test, read each test person's events and rewards. A person's steps show the container
each event was recorded in.

Extole keeps what a test person did. A unique event key records each key value once, and a rule
that counts a person's earlier events counts the earlier test events too. To run a test again
after you change the draft, use a new test person and new key values.

## View Draft Pages and Emails

A campaign preview sandbox renders a draft's creatives as well as its events. Open these addresses in a
browser on your program domain to see the draft before you publish it.

A page or an email is a document. This address returns the document itself:

```text
https://<your program domain>/zones/<zone name>?sandbox=campaign_preview-<campaign id>-<journey name>
```

The campaign editor's own preview uses this address, which also renders a JavaScript creative, such
as a share experience. Set `creative_classification` to `JAVASCRIPT`, `PAGE`, or `EMAIL`:

```text
https://<your program domain>/core/preview.html?zone_name=<zone name>&sandbox=campaign_preview-<campaign id>-<journey name>&creative_classification=JAVASCRIPT&is_preview_mode=true
```

### Check a Draft Without a Browser

The same `/zones/` address answers a plain HTTP request, with no token, so a script or an assistant
can check each experience of a draft:

- **An email** returns `text/html`, with the sender in the `X-Extole-Email-From` header and the
  subject in `X-Extole-Email-Subject`. Read the body for the heading, the message, and each amount.
- **A JavaScript creative**, such as a call-to-action or a share experience, returns
  `text/javascript`. The body carries the text the creative shows. A call-to-action that selects a
  JavaScript SDK zone in **Triggered By** renders only for a request from the JavaScript SDK, so
  send the header `x-extole-app-type: javascript_sdk`.
- **A zone the draft does not serve** returns `200` with an empty body, so check the content type
  and the length, not the status.

The zone name of an email is its `zoneName` setting. The zone name of a call-to-action is the
trigger event it selects. Each request records an input event in the `test` container.

```bash
curl -i -H "x-extole-app-type: javascript_sdk" \
  "https://<your program domain>/zones/homepage_banner?sandbox=campaign_preview-<campaign id>"
```

To find the program domain, the zone name, and the journey name, select the creative on the
campaign's **Assets** tab in My Extole and click **Preview in New Tab**. The address that opens
carries all three: the domain, the zone in `zone_name`, and the journey at the end of `sandbox`, such
as `MARKETING` or `SHARE`. A zone name that the campaign does not serve returns an empty page.

A preview has no person behind it, so a field that shows a person's details, such as a name, a share
link, or reward totals, shows the value the creative uses when there is no person. To check those
fields in an email, send a test email from the campaign editor. It sends the draft, built for the
person with the address you enter.

To see the published version of a page or an email, open the same `/zones/` address without the
`sandbox` parameter. A request with no sandbox uses a production sandbox, as
[Choose a Sandbox](#choose-a-sandbox) describes, so it renders what your live site renders for that
zone.

For the full procedure in My Extole, from **Apply** to **Publish Changes**, see
[Test a Change Before You Publish](/guides/programs-and-campaigns/managing-campaigns/test-a-change-before-you-publish).

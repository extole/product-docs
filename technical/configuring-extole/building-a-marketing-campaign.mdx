# Overview

Most programs start as a copy of a template, as [Creating a Program](/guides/platform-overview/creating-a-program)
describes. When no template has the flow you need, you build the marketing campaign from
components. [Configuration Concepts](/technical/configuring-extole/configuration-concepts)
explains what a component is and how you work with one. This page gives Extole's conventions for
laying a marketing campaign out, and what the platform evaluates for you.

One convention shapes the rest: **your systems send plain events, and the campaign does the
counting.** Send one event each time a person does something, with the identifiers of the people
and records involved. Put every count, time window, total, and limit in the campaign, where it
shows in Flow Builder and changes without a release of your systems. Do not ask your systems for a
running count, a total, or an event that says a person qualified.

To build the campaign with the Management API, see
[Build a Campaign from Components Over REST](/technical/platform-integrations/rest-apis/build-a-campaign-from-components-over-rest).
To build it in Flow Builder, see
[How to Add a New Business Event](/guides/flow-campaigns/how-to-add-a-new-business-event).

## Map the Program to the Campaign

| In the program | In the campaign | In the templates |
|---|---|---|
| Each kind of person | A role | `advocate` and `friend` in Refer A Friend, `participant` in Reward for Action |
| Each stage a person moves through | A journey in that role | A marketing journey for the promotion, and a journey for the actions that follow |
| Each action a person takes | A business event in that journey | `shared`, `signed_up`, `converted` |
| Each thing a person earns | A reward on the role of the person who earns it | Advocate Reward on Friend Converted |

- **One business event for each action**, even an action that only counts toward a later
  condition. Rules read the business events that the campaign records.
- **Name the business event after the action.** The name is the event name on the person's
  profile and in reports.
- **Put the business event in the role of the person who acts.** A reward for someone else reaches
  that person through a published event, as
  [Reward One Person for Another Person's Actions](#reward-one-person-for-another-persons-actions)
  describes.
- **Put each rule where its question is asked.** A journey's targeting decides who takes part. A
  business event's trigger rules decide when an event counts. A reward's rules decide whether the
  person qualifies.

## Order the Flow as the Events Happen

A campaign reads from top to bottom in the order its events take place. A program in which one
person brings in another runs in this order:

1. The first person sees and clicks the promotion: `promotion_viewed` and `promotion_clicked`, in a
   marketing journey.
2. The first person takes the action that brings them into the program.
3. The first person shares the invitation: `shared`, in a copy of the `share` journey.
4. The second person clicks the invitation: `share_clicked`, in a copy of the `new_customer`
   journey.
5. The second person takes the actions that count.
6. The first person's role records what those actions give back, in a later journey, and the
   rewards follow it.

A program for one person uses steps 1, 2, and 6. Keep the promotion and the invitation even when
the program description leaves them out: the promotion records how a person found the program,
and the share link ties the second person to the first. **Publish Event Data** uses that referral
relationship to find the first person, so the second person's events need no identifier for the
first person.

Flow Builder draws each role as a column and each journey as a row. Rows run in the order of each
journey's `sequence` setting, across all the roles, and the business events of a journey run in
the order of their own `sequence`. Number the journeys in the order of the flow, each with a
number of its own. Refer A Friend numbers the advocate's marketing journey 1, the advocate's share
journey 2, and the friend's journey 4. A role that acts at two points of the flow has a journey for
each point.

## Give Each Part What It Needs to Run

The Custom Campaign Template holds one role, one journey, and one business event, and no reward.
Every template that runs a program adds these parts, and your campaign needs them too:

| Part | What it needs | Guide |
|---|---|---|
| Business event | One trigger: the input event, zone, or published event that starts it | [How to Set Up Triggered By](/guides/flow-campaigns/how-to-set-up-triggered-by) |
| Journey | A targeting scenario, which decides who enters the journey | [How to Target a Program](/guides/flow-campaigns/how-to-target-a-program) |
| Reward | The business event that earns it, a reward supplier, and a reward email | [How to Add a New Reward](/guides/flow-campaigns/how-to-add-a-new-reward) |
| Reward | Reward rules for each condition on the reward | [How to Set Up Reward Rules](/guides/flow-campaigns/how-to-set-up-reward-rules) |

A new reward arrives with two reward rules: **Annual Reward Value Limit**, set to a total of 2,000
in a tax year that starts on January 1, and Business Event Quality, which passes when the earning
event's quality is high. Keep each rule your program needs, set it, and remove the others.

Give every reward a supplier from the start, even before your fulfillment exists. A custom reward
that Extole fulfills and sends by itself works as a placeholder: a test person earns the reward
and receives the reward email, and you replace the supplier when your fulfillment is ready.
[Build a Campaign from Components Over REST](/technical/platform-integrations/rest-apis/build-a-campaign-from-components-over-rest#use-a-placeholder-supplier-until-fulfillment-is-connected)
has the settings.

## What Extole Evaluates

| The program says | Put it in the campaign as |
|---|---|
| "Counts once for each order, account, or membership" | A unique event key on the business event's data. Extole records the business event once for each key value. See [Unique Event Keys](/technical/troubleshooting/duplicate-action-alerts-and-unique-event-keys#unique-event-keys). |
| "An order of \$40 or more" | **Value is greater than** on **Has Taken Action**, set to 40. It includes the number you set. **Event Value Greater Than** passes only above its number. |
| "Purchases add up to \$1,500" | **Has Taken Action** as a reward rule, with **Total value is greater than** set to 1500 and a **Recent Activity Window**. The total includes the event being evaluated and the number you set. |
| "Only after the person did something else" | **Has Taken Action** as a trigger rule on the business event. See [Common Trigger Rules](/guides/flow-campaigns/common-trigger-rules). |
| "At least 30 days after joining" | **Minimum Action Age** on that trigger rule. The earlier event counts only when it is at least that old. |
| "Within 30 days" | **Recent Activity Window** on **Has Taken Action**. |
| "On the third time" or "at least five times" | **Exact Count** or **Minimum Count** on **Has Taken Action**, as a reward rule. |
| "Unless they cancel" | **Has Not Taken Action**, with the business event that disqualifies the person. |
| "When someone they brought in does something" | **Publish Event Data** on the other person's business event. |
| "Once", or "once every six months" | **Reward Limit**, with **Maximum Count** and **Recent Activity Window**. A campaign with more than one reward sets **Applicable Reward Name** on each limit, so that each limit counts its own reward. |
| "No more than \$2,000 a year" | **Annual Reward Value Limit**, with the month and day the year starts. |
| "Once for each order or group" | **Reward Behavior** set to **Every Unique Action**, with **Unique Reward Data Parameter** set to the field that names the order or group. |
| "After a waiting period" | **Pending Period** on the reward. |
| "Only for some people" | A targeting scenario on the journey, or **Member of Audience** on the reward. |

A rule that compares or adds values reads the business event's value: the data item whose key type
is `VALUE`, such as the order amount. [Unique Event Keys](/technical/troubleshooting/duplicate-action-alerts-and-unique-event-keys#unique-event-keys)
describes key types.

A window is a duration, such as 30 days. On **Has Taken Action** it counts back from the time of
the event being evaluated. **Reward Limit** counts back from the moment the reward is evaluated. A
calendar month or quarter is a fixed period, and the nearest window is a duration of the same
length. A year can start on a date you set: **Annual Reward Value Limit** has a tax year start, and
**Reward Limit** has a tax year starting month.

**Has Taken Action** counts every matching event on the profile in the rule's scope. It counts
events, not distinct values, so give each counted event a unique event key when one record must
count once.

When a condition fits no row, see whether two business events make it fit. "Active for 30 days"
becomes the event that starts the clock and the event that shows the person is still there,
joined by **Has Taken Action** with a **Minimum Action Age**.

## Reward One Person for Another Person's Actions

**Has Taken Action** counts the events on the profile of the person the reward is for. When the
reward depends on what other people do, each counted action must reach that person's profile:

1. In the role of the person who acts, add a business event for the moment the action counts. Put
   its conditions on it as trigger rules, so the event is recorded only when they pass.
2. To count each person once, give that business event a unique event key from a field that
   identifies the person's place in the group, such as a membership ID. Extole reads the key from
   the inbound event, so trigger this business event with the input event itself.
3. Add **Publish Event Data** to that business event, and set **Target Role** to the role that
   earns the reward.
4. In the earning role, add a business event that the published event triggers.
5. On the reward, add **Has Taken Action** as a reward rule on the business event from step 4,
   with the count you need.

**Person Identification** on **Publish Event Data** decides who receives the event. It arrives
with **Person Identified by Referral Relationship**, which sends the event to the person who
invited the actor. To send the event to a person named in the event data, replace it:

| Person identification | Who receives the event |
|---|---|
| **Person Identified by Identity Key** | The person with the identity key, such as an email, in the event data. |
| **Person Identified By Alternate Person Key** | The person with the person key, such as a partner user ID, in the event data. |
| **Person Identified by Extole Person ID** | The person with the Extole person ID in the event data. |

[How to Set Up Bonus Rewards on a Specific Referral Count](/guides/flow-campaigns/how-to-set-up-bonus-rewards-on-a-specific-referral-count-2nd-3rd-5th-etc)
shows steps 3 to 5 in Flow Builder.

## Test Each Condition from Both Sides

Before you publish, test the draft with test people:

- For each reward, a test person whose events earn it.
- For each window, count, threshold, and exclusion, a test person whose events fall just outside it
  and earn nothing. Back-date events with `event_time` to put them where the window needs them.

[Test a Campaign Draft Over REST](/technical/platform-integrations/rest-apis/test-a-campaign-draft-over-rest)
covers how to send the events and read the result.

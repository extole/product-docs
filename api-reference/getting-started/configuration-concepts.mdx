# Overview

Everything you configure in Extole is a **component**. A marketing campaign is a component, and so are the journeys, business events, rewards, and experiences inside it. Each component describes what it does and which settings it offers, so you learn the details from the component and not from a static list.

An account holds four kinds of top-level component:

## How the Components Relate

A top-level component holds its own copy of every component inside it. A change to a business event in one marketing campaign reaches that campaign and no other.

| Top-level component | Components inside it |
|---|---|
| Marketing campaign | Roles, such as advocate and friend. Each role has journeys and rewards. A journey has business events. A business event has rules, actions, and experiences. |
| Integration | The events and actions it exchanges with the external system, its views in My Extole, and the reward suppliers a partner fulfills through. |
| Extension | Whatever the capability needs: views, jobs, events, experiences, or monitors. |
| Account configuration | Shared settings. Every account has one named `global`. |

Top-level components also work together. An integration or an extension declares the events an external system can send, and a business event in a marketing campaign chooses one of them as its trigger. [How to Set Up Triggered By](/guides/flow-campaigns/how-to-set-up-triggered-by) covers that choice.

An account resource is used by reference. A reward names its reward supplier and a campaign names the audiences it targets, so one reward supplier can serve many campaigns, and a change to it reaches all of them.

A **program** is a group of marketing campaigns that serve one audience and one outcome. The campaigns of a program share a `PROGRAM` label. [Programs vs. Campaigns](/guides/platform-overview/key-concepts/programs-vs-campaigns) explains when to make a new one of each.

## Working with Components

You work with every component the same way, in My Extole or through the [Management API](/api-reference/getting-started/api-overview#management-api).

1. **Discover the component.** [List components](/api-reference/components/list-components) returns the components your account has, and you can narrow the list by type, tag, or parent component. [List duplicatable components](/api-reference/components/list-duplicatable-components) returns the components you can copy into your account: the ones Extole maintains and the ones you already have.
2. **Read what it says about itself.** [Get a component](/api-reference/components/get-a-component) returns its name, description, and types. [List component settings](/api-reference/components/list-component-settings) returns each setting with its own name, description, and type.
3. **Configure its settings.** A component has two kinds of setting:
   - A **variable** holds a value, such as a text, a color, a reward supplier, or an audience. [Update a component setting](/api-reference/components/update-a-component-setting) sets it.
   - A **socket** holds other components, and it says which types it accepts. [Add component to setting](/api-reference/components/add-component-to-setting) copies a component into a socket. To see what fits a socket, list duplicatable components with that socket as the target.
4. **Validate the result.** [Get a built component](/api-reference/components/get-a-built-component) returns the component as Extole will run it. [Test a Campaign Draft Over REST](/technical/platform-integrations/rest-apis/test-a-campaign-draft-over-rest) sends events to a draft before you publish it.

[Component Settings Over REST](/technical/platform-integrations/rest-apis/component-settings-over-rest) covers reading and writing a setting in detail.

### Configuration and Modification

A component you copy remembers the component it came from, which is its **origin**. When the origin gets a later version, [Upgrade a component](/api-reference/components/upgrade-a-component) brings your copy to that version, and [Get available component upgrades](/api-reference/components/get-available-component-upgrades) lists what an upgrade would bring.

An upgrade keeps what you configured: the values you set on settings, the settings and assets you added, and the components you placed in sockets. Everything beneath the settings comes from the new version of the origin.

So there are two ways to change what a component does, and they are not equal:

- **Configuring** a component sets its variables and fills its sockets. An upgrade carries that work forward.
- **Modifying** a component changes the [model elements](/technical/integration-overview/underlying-configuration-model#model-elements) beneath it, such as a trigger or an action. An upgrade replaces those elements with the origin's, so your copy no longer upgrades automatically: each upgrade means making the change again.

Modify model elements as a last resort. When a component has no setting for the behavior you need, or its description doesn't say how to get it, look for another component that offers it. If none does, the component is missing a setting or a description, and Extole Support can tell you whether it can gain one.

## The Configuration Lifecycle

Configuration becomes behavior in three stages.

```
Configuration  ──►  Build Time  ──►  Runtime
component           built component  events, journeys, rewards
```

| Stage | What exists | What happens |
|---|---|---|
| **Configuration** | The component: its types, its variables and sockets, and its model elements. | You discover, configure, and save. Editing a published campaign creates a draft. |
| **Build time** | The built component. | Each save builds the campaign. Building resolves every value that can be known from configuration alone. |
| **Runtime** | The built model elements, running. | Extole receives events and runs the configured behavior. A value that depends on the event or the person is resolved here. |

A **component** is what you configured. A **built component** is what the build made of it. The two can differ, because a setting can hold an expression and the built component holds the result.

A built component can still hold unresolved values. A greeting that includes the person's first name has no value until a person arrives, so the built component keeps the expression and the runtime resolves it for each person.

## What Configuration Does at Runtime

At runtime, Extole works with events and people. The configuration decides what happens to each event.

1. An **event** arrives from your site, your app, your servers, a file, or an integration. Extole finds or creates the **profile** of the person it belongs to.
2. **Targeting** finds the **business events** this event can start, across your campaigns, and chooses the campaign that applies to this person. The audiences and **rules** you configured decide which campaign that is, whether the event qualifies, and what its quality is.
3. Extole records the business event as a **step** in the person's **journey**.
4. The business event's **actions** run: show an experience, send an email, call a webhook, or earn a **reward**. A reward has its own rules, and its reward supplier fulfills it.

The profile now holds the step and the reward, and they shape what the person is eligible for on the next event. [Key Concepts](/technical/integration-overview/key-concepts) describes each of these in more depth.

## The Model Beneath Components

Components are built from model elements, such as campaigns, steps, triggers, and webhooks. You don't need them to configure Extole. [The Underlying Configuration Model](/technical/integration-overview/underlying-configuration-model) describes them for developers who build components, troubleshoot a campaign in depth, or read `campaign_type` in the Management API.

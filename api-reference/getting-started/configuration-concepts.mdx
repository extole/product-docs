# Overview

Use this page when calling the Management API or reading campaign configuration. It describes how configuration is structured: a campaign is a tree of components plugged into typed sockets.

Each of these concepts has a **runtime** meaning and a **configuration** meaning. At **runtime**, a campaign is the thing that accepted an event, a reward is one a person earned, and a journey is the path that person took. The [Integration APIs](/api-reference/getting-started/api-overview#the-apis) work with that meaning, and [Key Concepts](/technical/integration-overview/key-concepts) explains it.

In **configuration**, a campaign is a tree of components, a reward is a reward component with its rules and supplier, and a journey is a component that groups business events. The [Management API](/api-reference/getting-started/api-overview#management-api) and My Extole work with that meaning. This page explains it.

## Components

A component is the unit of configuration. Everything you set up in a campaign is one: a role, a journey, a business event, a reward, an experience, a rule. A component has a name, one or more types, settings, and child components. Together, the components of a campaign form a tree whose root is the campaign. The campaign's root component sits under the root of the account's `global` campaign, which holds the My Account settings, so a setting can take its value from either one. See [Copies, Inheritance, and Upgrades](/technical/integration-overview/copies-inheritance-and-upgrades).

[List components](/api-reference/components/list-components) returns the components of an account. [Get a built component](/api-reference/components/get-a-built-component) returns one with every setting evaluated.

## Types

A component's type decides which settings it carries and which child components it can hold. Type names carry a generation suffix, such as `business-event-v10.0`. The pages on this site drop the suffix when they name a type in prose.

A type can specialize another. `reward-email-v10.0` is a kind of `reward-send-action-v10.0`, which is a kind of `action-v10.0`. A socket that accepts the general type accepts each specialized one.

## Sockets

A **socket** is a typed slot for child components — a setting that holds one component or many. A `SOCKET` holds one. A `MULTI_SOCKET` holds many. Each socket declares the types it accepts, so a `businessEvents` socket on a journey holds business events and nothing else.

You add to a campaign by copying a component into a socket. The API lists those sources as [duplicatable components](/api-reference/components/list-duplicatable-components) — templates you can install. Pass a target component and setting to see only the ones that fit that socket. [Duplicate a component](/api-reference/components/duplicate-a-component) installs the copy. The sources are the components Extole maintains and the ones your account already has.

For example, to add a reward, list duplicatable components for the campaign's `rewards` socket, then duplicate one into that socket. The copy starts with the source's settings, child components, and creatives as they were when you copied it, and from then on it belongs to the campaign. Later changes to the source reach the copy through an [upgrade](/technical/integration-overview/copies-inheritance-and-upgrades#upgrades).

## Variables

A variable is a setting with a value. Each has a type, such as `STRING`, `COLOR`, `BOOLEAN`, `REWARD_SUPPLIER_ID` or `TRIGGER_CONFIGURATION`, and a map of values that can differ by locale. [List component settings](/api-reference/components/list-component-settings) returns the variables and sockets of a component.

A duplicated component holds the values its source had when it was copied. Each variable also has a `source` that decides where its value comes from:

* `LOCAL`: the value stored on this component.
* `INHERITED`: the same-named variable on the nearest ancestor component that is not itself `INHERITED`, up through the campaign root to the account's `global` campaign. The ancestor's published value is used.
* `PARAMETER`: the same-named parameter of the socket the component is installed in.

Values are evaluated when the campaign is built, which is why [Get a built component](/api-reference/components/get-a-built-component) and the component as configured can differ. For an `INHERITED` variable, the built component returns the value in effect.

Some variable types reference configuration that lives outside any campaign. `REWARD_SUPPLIER_ID` names a reward supplier, `AUDIENCE_ID` an audience, `WEBHOOK_ID` a webhook. The campaign refers to them; the Management API's [Reward Suppliers](/api-reference/reward-suppliers/list-reward-suppliers), [Audiences](/api-reference/audiences/list-audiences) and [Webhooks](/api-reference/webhooks/list-webhooks) groups manage them.

## The Four Kinds of Campaign

An account's campaign list holds four kinds. The Management API carries the kind as `campaign_type`.

| `campaign_type` | What it is |
|---|---|
| `MARKETING` | A participant-facing campaign in a program: roles, journeys, business events, rewards, and the content served on zones. These are the campaigns on the My Extole **Programs** page. |
| `CONFIGURATION` | Account configuration, not a participant-facing program. The account's `global` campaign is one. It holds variables and components that the account's other campaigns use, and its root holds the My Account settings that `INHERITED` variables resolve to. |
| `INTEGRATION` | A connection to an outside platform: partner events mapped onto business events, outbound webhooks, and the reward suppliers a partner fulfills through. The tiles on the **Integrations** page. See [Build a Partner Integration with the Management API](/technical/building-partner-integrations/integration-lifecycle/management-api-integration). |
| `EXTENSION` | A capability added to the account: views in My Extole, scheduled jobs, mobile SDK platforms, tagless calls to action, and monitoring. Usually Extole-maintained rather than built by an outside developer. |

[Create a campaign](/api-reference/campaigns/create-a-campaign) takes the kind. [List campaigns](/api-reference/campaigns/list-campaigns) returns all four.

## A Marketing Campaign as a Tree

The socket names below are the ones the API returns, and the type names drop their suffix. Each line is `socketName: component-type` — children listed under a socket are the types that socket accepts.

```
campaign
└─ roles: role                        advocate, friend
   ├─ journeys: journey
   │  ├─ targetingScenario: targeting-scenario
   │  │     entryRules, ongoingRules: rule
   │  ├─ businessEvents: business-event
   │  │     triggerRules, qualificationRules, qualityRules: rule
   │  │     actions, lowQualityActions: action
   │  │     experiences, onsitePromotions, clickBehavior: content
   │  │     emailPromotions: email-promotion ── actions: action
   │  │     data: data
   │  ├─ rules: rule
   │  ├─ shareLinkActions: content
   │  ├─ authenticationActions: authentication-action
   │  └─ data: data
   └─ rewards: reward
         triggerRules: rule
         rewardRules: reward-rule
         rewardIssuer: reward-issuer
            sendActions: reward-send-action ── reward-email
            fulfillmentActions: action
         data: data
```

Flow Builder shows the same tree. Its columns are the roles, its flows are the journeys, its white boxes are the business events, and the promotions, experiences, quality rules, and actions on each business event are the children of that component. Rewards hang under the role in this tree; Flow Builder surfaces them next to the business events that earn them. [Flow Campaigns](/guides/flow-campaigns/index) describes each element as a marketer sees it.

The leaf types have structure of their own:

- **content** is a creative, a page or an experience. It holds content blocks in layout sockets, nested experiences, and the trigger events that show it.
- **action** is what a business event does: send an email, publish an event, send a reward. It holds data and a person identification that says which person the action is about.
- **rule** is a condition. A group rule holds rules. A targetable event listener is a rule that listens for a journey step — the named milestone recorded after a business event matches.
- **business-event** declares the event a campaign listens for. Once a campaign accepts an event that matches one, the person's journey records a step with that name.
- **reward** holds the rules that decide whether one is owed and the issuer that sends and fulfills it.
- **data** declares the fields a component captures or carries.

## Extensions and Integrations as Trees

```
extension                              integration
├─ views: view                         ├─ views: event-stream-view
├─ jobs: job                           └─ rewardSuppliers: reward-supplier
│    triggers: job-trigger
│    tasks: job-task ── events: job-event
├─ integrationEvents: event-api-trigger-event
├─ platforms: mobile-sdk-platform ── ctas: sdk-zone-event
├─ zoneEvents: sdk-zone-event
├─ taglessCtas: tagless-cta
├─ experiences: content
└─ monitoringElements: monitoring-element
```

An extension's `integrationEvents` are the events an outside system can send to the account. A marketing campaign's business event is triggered by one of them, which is what **Triggered By** selects in Flow Builder. [How to Set Up Triggered By](/guides/flow-campaigns/how-to-set-up-triggered-by) covers that choice.

## Programs, Labels, Versions and State

In product language, a **program** is the use case — audience plus outcome. In the Management API, that grouping is represented as a `PROGRAM` label: every campaign carries one, and the campaigns that share a label are one program. No component represents a program, because the component tree starts at the campaign, so a program has no settings of its own. A campaign can also carry `CAMPAIGN` and `JOURNEY` labels. An integration's events name the program label they are for, and that label is what targets them at the campaign. [Programs vs. Campaigns](/guides/platform-overview/key-concepts/programs-vs-campaigns) explains when to make a new one of each.

A campaign has **versions**. Editing creates a draft, and publishing makes the draft the published version. Building evaluates every variable of a version into the built campaign the runtime uses. Publishing builds the campaign from its own components and keeps the library versions they already hold.

A campaign has a **state**: `NOT_LAUNCHED`, `LIVE`, `PAUSED`, `ENDED`, `STOPPED` or `ARCHIVED`. The state decides whether the runtime considers the campaign for an event. [Pausing, Ending, and Scheduling Campaigns](/guides/programs-and-campaigns/managing-campaigns/pausing-ending-and-scheduling-campaigns) covers the transitions in My Extole.

## Configuration Outside Campaigns

Some configuration belongs to the account, not to any campaign: users and their roles, program domains, email sending domains, security keys, reward suppliers, audiences, webhooks, event streams, and report schedules. Each is a group of the Management API. A campaign refers to them through its variables, so the same reward supplier can serve many campaigns and a change to it reaches all of them.
